## Analysis Findings

### Write optimized 

Writing is 3.5x more costly than reading, therefore, a wide N means fewer threadgroups writing to C, and each write covers 128 col, making them perfectly coalesced.





  Writes are the bottleneck, not reads. At 165 GB/s write vs 571 GB/s read, your output tile write-back is 3.5x more expensive than loading A/B tiles. This means:                                                                               
  - Maximize compute per output element — use the biggest accumulator tile you can (24 accumulators, right before the spill cliff)
  - The C matrix write-back should be coalesced float4 writes, never scattered                                                                                                                                                                   
  - Fusing operations that avoid writing intermediates to DRAM (fused attention, fused GELU) gets a 3.5x multiplier on the memory side
                                                                                                                                                                                                                                                 
  Don't double-buffer unless your tiles are huge. Staging through shared memory costs 14%. On M4 with dynamic caching, the hardware is already managing the cache well. Double-buffering only wins if your MMA compute time exceeds that 14%     
  overhead — which means your K-dimension tile needs to be fat enough (~64+ columns) to keep the ALU busy during the staging penalty.                                                                                                            
                                                                                                                                                                                                                                                 
  You need at least 4096 threads to saturate DRAM, but 16K thrashes cache. For a GEMM dispatch:                                                                                                                                                  
  - 10 threadgroups of 256 threads = 2560 threads — undersaturated, you're leaving bandwidth on the table
  - 16 threadgroups of 256 = 4096 — sweet spot for DRAM bandwidth                                                                                                                                                                                
  - Beyond ~64 threadgroups the working set spills and bandwidth drops
  - This means for small GEMMs (M or N < 128), you can't saturate the memory bus                                                                                                                                                                 
                                                                                                                                                                                                                                                 
  Latency is 5x worse under load — prefetching is mandatory. The 43ns L1 latency from our probe is fiction during real execution — it's 300ns+ when anything else is running. Your GEMM inner loop must have loads issued 5+ iterations ahead of 
  consumption. Concretely: if your MMA takes ~0.3ns per op and you need 24 of them, that's ~7ns of compute. You need loads dispatched ~300ns / 7ns ≈ 40+ MMA iterations ahead. This means deep software pipelining with large K-tiles.           
                                                                                                                                                                                                                                                 
  Use 8 or 32 counters for split-K reductions, never 10. If you're splitting the K dimension across threadgroups and reducing with atomics, the 10-counter anomaly means a 10-way split (matching core count) is actually slower than 8-way. Use 
  powers of 2.                                              
                                                                                                                                                                                                                                                 
  Per-core bandwidth is 14.8 GB/s — plan tile sizes around this. Each core can pull ~14.8 GB/s. For a 256-thread threadgroup doing MMA at 2.6 TFLOPS (from our probe), the arithmetic intensity needed to not be memory-bound is:                
  - 2600 GFLOPS / 14.8 GB/s = 176 FLOPS/byte
  - An 8x8 MMA does 128 FLOPS on 512 bytes of input = 0.25 FLOPS/byte                                                                                                                                                                            
  - You need to reuse each loaded byte ~700x — that's what the tile size determines
  - A 64×64 output tile with K=64 gives reuse of ~64x per byte, still memory-bound                                                                                                                                                               
  - A 128×128 output tile with K=64 gives ~128x reuse — getting closer but still short                                                                                                                                                           
  - This confirms: M4 GEMM is memory-bound for all practical matrix sizes unless you hit L1/SLC                                                                                                                                                  
                                                                                                                                                                                                                                                 
  Dynamic caching means no fixed "optimal tile size". The cache boundaries aren't fixed — they shift under load. A tile configuration that fits perfectly in "L1" during testing might not fit during real inference when attention and FFN      
  compete for cache. Build your tile selection to be conservative — assume 50% of the cache sizes you measure.
