⏺ Yes — you're right, and that's the better pick for kv_state. Half the TG
  footprint (4KB vs 8KB for 64×64) at effectively the same latency (0.6% is
  noise) is a free win.

  The one caveat: mamba's state accumulates across chunks (S_new = decay·S_prev 
  + K_decayed^T @ V), so half's ~3-decimal-digit mantissa can compound error
  over long sequences. Standard fix:

  - Store kv_state as threadgroup half[HEAD_DIM * HEAD_DIM]
  - Accumulate into float registers (Tile<...> is already fp32 accum via
  simdgroup_matrix)
  - Write back as half at the chunk boundary

  That's what the chip-analysis numbers already reflect — the threadgroup_half
  bench loads into float regs for compute. You get the 50% memory savings and
  the numerical stability.

  One thing to verify: for a 2048-length sequence with 16 chunks, the
  accumulated rounding in half is usually fine for inference but can drift
  noticeably in training. Since you're targeting inference on M2+, half storage
  is the right call.

⏺ 1. Benchmark: run MLX's mamba_mlx.py and your kernel on identical [B, H, N, D]
   inputs, compare wall time and max abs error — MLX is your correctness oracle
  and your speed target.
  2. Keep it one fused kernel: splitting SSM from the rest costs you ~131 us per
   extra dispatch, which dominates the SSM math itself at chunk scale.
  3. The projections (in_proj, out_proj, conv1d) stay separate — different tile
  shapes, different register pressure, no shared threadgroup state.
  4. So: fwd.metal = one kernel doing cumsum + decay + QK^T + intra-chunk +
  inter-chunk state update + output, and projections are their own kernels
  called before/after.
  5. Don't rename to ssm.metal — fwd.metal is the whole SSD block, and splitting
   it loses the threadgroup reuse that makes fusion win.

❯ for benchmarking, how should we test? a full fwd pass? how long it takes for  
mlx vs our fwd? the # tokens/sec? or something else? explain                    

⏺ Three things to measure, in order of importance:

  1. Per-kernel latency (µs) — the core number. Fix a shape (e.g. B=1, H=32, 
  N=2048, D=64), warm up 10 iterations, then time 100+ runs and take the median.
   This is what tells you if your kernel beats MLX's SSD block head-to-head. Use
   MTLCommandBuffer's GPU start/end timestamps, not wall clock — wall clock
  includes host dispatch noise.

  2. Correctness (max abs error) — run MLX's mamba forward on the same inputs,
  compare outputs elementwise. For fp16 accumulated in fp32, < 1e-2 max abs
  error is normal; anything larger means a bug.

  3. Tokens/sec — only meaningful at the full model level (all kernels chained:
  in_proj → conv → SSD → out_proj). This is what a user feels. Report it once
  you have the whole pipeline, not before — per-kernel µs is what you optimize
  against day-to-day.

  What to sweep: seq lengths [512, 1024, 2048, 4096, 8192] at fixed H, D. MLX
  will scale badly at long N because it's not fused; that's where you win and
  the graph tells the story.

  Don't bother with: FLOPs/sec, arithmetic intensity charts, roofline plots —
  they're post-hoc justifications, not the number you ship against. Latency and
  correctness are the only two that matter until the kernel is fast.
